# 金标标注协议（切片 8.0）

> 两个 Agent 独立盲标同一批案件，机械比对出分歧，人工仲裁分歧。
> 本文件是**分工的唯一依据**——不按本文件标注的结果不予采纳。

---

## 1. 为什么金标分两层

合成数据是**按规则生成的**，所以有些答案在生成时就已经知道，不必任何人去标。

| 层 | 内容 | 来源 | 覆盖指标 |
| --- | --- | --- | --- |
| **技术性真值** | 事实取值、规则应命中 / 不适用 / 未判定、适用版本、严重度、覆盖度三类计数、未判定原因码 | **生成器直接产出**（`src/finguard/eval/synth.py`） | Q-01 / 02 / 03 / 06 / 07 / 08 / 09、SEC-01~05、P-10 |
| **判断性标注** | 识读是否正确、规则适用性是否认同、理由是否成立、严重度是否恰当、是否算误报 | **两个 Agent 各标一半**（本协议） | Q-04、Q-05、P-03、P-04、P-06 |

**技术性真值不交给 Agent 标**——用不确定的手段去确定已知的事，是纯粹的浪费且引入噪声。

---

## 2. 分工与盲评纪律

| 角色 | 负责 | 纪律 |
| --- | --- | --- |
| 实现方 Agent（`feat/impl`） | 标注 A 组（奇数号案件） | **不得**读取 B 组的任何标注文件 |
| 评审方 Agent（`review/impl`） | 标注 B 组（偶数号案件） | **不得**读取 A 组的任何标注文件 |
| 仲裁（人工） | 分歧项 | 只看分歧清单与两份理由，不看真值 |

硬约束：

1. **裁判看不到技术真值**——任务包 `materials.jsonl` 里没有真值字段；真值在 `truth.jsonl`，只给系统比对用
2. **裁判看不到系统输出**——本轮标的是「材料读出来是什么」，不是「系统判成了什么」
3. **两边互不可见**——这是"盲"的意义；同一上下文里标过 A 再标 B 不算盲评
4. **同一版规则**——`manifest.json` 的 `rules_fingerprint` 必须一致；不一致时分歧可能只是规则变了
5. **枚举封闭**——五个字段的取值必须落在 `LABEL_SCALES` 内；自由文本无法机械比对
6. **盲标批次必须是裁判没见过的批次**——实现方在开发生成器时**必然**见过早期批次的真值，
   因此那些案件不能作盲标样本；须换 seed / 前缀生成**全新批次**（`--prefix FG-B`）才可标

## 3. 标注规范（五个字段）

裁判只看材料，按下表逐项判断。

### 3.1 `fact_recognition_ok` —— 从材料里读出来的要素是否与事实一致

| 取值 | 口径 |
| --- | --- |
| `对` | **规则所需要素**都能从材料中明确读出、无歧义，裁判读出的值与材料一致 |
| `错` | 要素能读出但材料本身矛盾 / 歧义，读不出唯一值 |
| `缺漏` | 材料里缺某条规则所需的要素 |

> 判"读对没有"以**材料文本**为准，不以任何抽取工具的输出为准——
> 裁判就是那个"抽取工具"，他判断的是"规则要的要素材料里给全了没有"。
> 判定范围是**规则所需要素**，不是材料里出现的一切。

### 3.2 `rule_applicability` —— 规则适用性判断是否认同

| 取值 | 口径 |
| --- | --- |
| `同意` | 认同该条规则的适用 / 不适用 / 须人工判定判断 |
| `不同意` | 不认同，**必须**在 `notes` 写明理由（哪条规则、为什么不认同） |

> 这是唯一允许写理由的字段；其他字段的理由统一放 `notes`。

### 3.3 `reason_quality` —— 理由是否成立

| 取值 | 口径 |
| --- | --- |
| `成立` | 理由能被材料直接支撑，无跳跃 |
| `部分成立` | 方向对但有跳跃，或只用了一半的依据 |
| `不成立` | 材料不支持该结论 |
| **`不适用`** | 本案无任何命中意见，**无理由可评** |

### 3.4 `severity_appropriate` —— 严重度是否恰当

| 取值 | 口径 |
| --- | --- |
| `恰当` | 与规则库定义的严重度一致 |
| `偏高` | 实际情形比规则库的严重度轻 |
| `偏低` | 实际情形比规则库的严重度重 |
| **`不适用`** | 本案无命中意见，**无严重度可评** |

> 严重度**只能来自规则库**（FR-AUDIT-03），裁判判的是"规则库给的这档对不对"，不是"应该给哪档"。

### 3.5 `is_false_positive` —— 是否算误报

| 取值 | 口径 |
| --- | --- |
| `是` | 核查后确认这条预警不成立 |
| `否` | 成立 |
| `无法判断` | 材料不足以判断（缺关键证据） |
| **`不适用`** | 本案无命中意见，**无对象可判** |

## 4. 输出格式

每行一个 JSON 对象，写到 `data/gold/labels/<标注人>.jsonl`：

```json
{
  "case_id": "FG-G-0001",
  "annotator": "impl-agent",
  "labels": {
    "fact_recognition_ok": "对",
    "rule_applicability": "同意",
    "reason_quality": "成立",
    "severity_appropriate": "恰当",
    "is_false_positive": "否"
  },
  "notes": "",
  "labeled_at": "2026-11-28"
}
```

校验：`python scripts/compare_gold.py --check data/gold/labels/impl-agent.jsonl`

## 5. 仲裁规则

1. 两边一致 → 直接作为金标
2. 两边分歧 → 进仲裁清单，**逐条**裁决，裁决结果写进 `data/gold/labels/resolved.jsonl`
3. 仲裁时的优先级：
   - `rule_applicability` 分歧 → 以**技术真值**为准（生成器用的就是它）
   - `severity_appropriate` 分歧 → 以**规则库**为准，并记录"规则库的档位在此情形下不适用"作为规则改进线索
   - 其余字段分歧 → 人工判断，或回到材料重读
4. 仲裁后重算一致率，**分歧率本身进评测报告**——它是标注难度的度量，也是"标注规范是否够清楚"的信号

## 7. 第一轮试点发现（5 个缺陷，均已修）

试点 = 实现方先标 5 件。这 5 件是**真读材料、真做判断**的，不是走过场——
于是暴露了 5 个只有真做才会暴露的缺陷：

| # | 缺陷 | 后果 | 修法 |
| --- | --- | --- | --- |
| 1 | 任务包**缺规则清单** | 裁判无法判断"规则适用性"——它不知道有哪些规则 | 任务包补 `rules`（按 rule_id 分组，含 scope / 生效区间 / 严重度 / DSL）。**规则对所有审查岗可读，给它不泄漏判定结果** |
| 2 | 材料**缺「机构层级」** | 机构层级是三键之一，R-CR-050 按它限定 → 裁判无法判断该条是否适用 | 申请要素表补「机构层级」 |
| 3 | 材料**缺「产品类型」** | 同上，产品类型是三键之二，且是多数规则的 scope 维度 | 申请要素表补「产品类型」 |
| 4 | 三个字段在**无命中意见时无对象** | 枚举里没有出口，裁判被迫给无意义取值，一致率统计掺噪声 | 枚举补「不适用」 |
| 5 | **角色冲突**：实现方在调试生成器时已见过早期批次的真值 | 那些案件不可能算盲标 | 换 seed / 前缀生成**全新批次**（`FG-B`），实现方从未见过其真值；manifest 记 `blind_batch` |

> 第 5 条是方法论上最重要的一条：**盲标的前提是裁判没见过答案**。
> 开发者天然见过自己系统的输出，让他标自己系统的金标，盲性就破了。

## 8. 复现命令

```bash
# 重新生成任务包（同一 seed → 同一批材料）
python scripts/build_gold_pack.py --count 30 --seed 20261128

# 校验一份标注
python scripts/compare_gold.py --check data/gold/labels/impl-agent.jsonl

# 比对两份标注，出一致率与分歧清单
python scripts/compare_gold.py \
    --left data/gold/labels/impl-agent.jsonl \
    --right data/gold/labels/review-agent.jsonl \
    --truth data/gold/pack/truth.jsonl
```
